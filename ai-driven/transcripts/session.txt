  **How it works:** every winning pattern is a list of 4 `[row, col]` cells. The list of patterns (`WIN_PATTERNS`) is built once when the module loads. Each call then only reads cells: for each pattern it takes the first cell, skips the pattern if that cell is empty, and otherwise checks that the other 3 cells match it. It returns on the first match, so when both players have a win, whichever pattern comes first in the list decides.

  ```ts
  for (const [[r0, c0], ...rest] of WIN_PATTERNS) {
    const first = board[r0][c0];
    if (first && rest.every(([r, c]) => board[r][c] === first)) return first;
  }
  return null;
  ```

  **The 19 patterns**

  | Condition | Count | Cells |
  |---|---|---|
  | Horizontal | 4 | row `r`: `(r,0) (r,1) (r,2) (r,3)` |

  **Avoiding repeated work**
  - **No per-call setup:** the patterns are worked out once, not on every call.
  - **No per-player pass:** the first cell of each pattern decides which player to compare against, so it checks X and O together.
  - **Early exits:**
    - an empty first cell skips the pattern after one read;
    - `every` stops at the first cell that doesn't match;
    - the loop stops at the first winning pattern.
  - **Worst case:** a board with no winner reads 76 cells (19 patterns × 4 cells).

  A further shortcut, returning early when a player has fewer than 4 pieces on the board, would cost an extra pass over every cell, so I didn't add it.

  ## Fewer reads: two options

  Right now each cell can be read up to about 6 times, once for each pattern it belongs to, for 76 reads in the worst case. Both options below read each of the 16 cells exactly once.

  **A. One running total per pattern.** Count X as +1, O as −1 and empty as 0, and keep a total for each of the 19 patterns. A total of +4 is only possible if all four cells are X, and −4 only if all four are O.

  ```ts
  // Built once: for each cell, the numbers of the patterns that contain it.
  const sums = new Array(19).fill(0);
  for (let r = 0; r < 4; r++)
    for (let c = 0; c < 4; c++) {
      const v = board[r][c] === 'X' ? 1 : board[r][c] === 'O' ? -1 : 0;
      if (!v) continue;
      for (const p of PATTERNS_FOR_CELL[r][c]) {
        sums[p] += v;
        if (Math.abs(sums[p]) === 4) return v > 0 ? 'X' : 'O';
      }
    }
  return null;
  ```

  This cuts reads from 76 to 16, but each filled cell still updates every total it belongs to, so the worst case is still 76 updates. The work has moved, not shrunk. It also needs an extra lookup table from each cell to its patterns.

  **B. Represent each player's pieces as one number.** There are 16 cells, so each player's pieces fit in a 16-bit number, with bit `r*4 + c` set when they own that cell. Each pattern also becomes a 16-bit number (its "mask"), and a player wins if every bit in a pattern's mask is set in their number.

  ```ts
  const MASKS = WIN_PATTERNS.map((p) => p.reduce((m, [r, c]) => m | (1 << (r * 4 + c)), 0));

  let x = 0, o = 0;
  board.forEach((row, r) => row.forEach((v, c) => {
    if (v === 'X') x |= 1 << (r * 4 + c);
    else if (v === 'O') o |= 1 << (r * 4 + c);
  }));
  for (const m of MASKS) {
    if ((x & m) === m) return 'X';
    if ((o & m) === m) return 'O';
  }
  return null;
  ```

  This takes 16 reads, then 19 checks that are each a single bitwise AND and compare. `anyMovesLeft` would become `(x | o) !== 0xFFFF`. Game engines commonly use this technique. One limit: JavaScript bitwise operators only work on 32 bits, so beyond a 5×5 board you'd need `BigInt`.

  ## My recommendation: keep what we have

  - **The current version often reads far fewer than 76 cells.** It skips a pattern as soon as its first cell is empty or a cell doesn't match, so a sparse board costs much less than the worst case. The 16-read options always read all 16 cells.
  - **The speed difference isn't measurable here.** A cell read is a simple array lookup, and at 4×4 we're comparing about 76 cheap operations with about 35.
  - **The current version is the easiest to check by eye.** A reviewer can compare the list of patterns directly against the five win conditions in the prompt. Bit masks and running totals are harder to verify.
  - **The real saving needs a stateful API, which we ruled out.** If the solver knew which move was just played, it would only need to check the 3–7 patterns that pass through that cell. That is far less work than any full scan.

  Option B is the one worth building if you want to show a performance-minded approach. It would be a small change, and the existing 50 tests would cover it without changes.
